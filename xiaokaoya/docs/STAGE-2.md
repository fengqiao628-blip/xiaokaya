# 第二阶段：本地数据安全

版本0.2.0，数据库V2，完整备份格式版本1。只实现完整 JSON 导出恢复、CSV、快照、预检、版本迁移和失败保护。第三至八阶段的业务功能没有提前开发。

## 不变合同

保留 React / Vite / Electron / Dexie。appId、NSIS GUID、userData、profile、默认持久 Session、app://xiaokaoya 和数据库名称均沿用第一阶段固定值。重大调整须先说明原因与风险并确认。

## 数据版本

V1_SCHEMA 保留原表和索引。V2_SCHEMA 只追加 datasetMeta（唯一 dataset 行、稳定 datasetId、创建时间）及 migrationHistory（版本起止、执行时间、升级前快照 ID）。

旧库通过原生 IndexedDB 以现有版本读取，完成一致性文件快照和回读校验后，才给 Dexie 升级事务授权。未保护的 V1→V2 直接打开会中止升级。数据库实例构造不会自动开启旧库。

## 完整备份合同

format、formatVersion、schemaVersion、appVersion、backupId、datasetId、exportedAt、purpose、counts、data、checksum。SHA-256 覆盖除 checksum 外的完整规范化对象。清单与实际表必须完全对应，未知表和字段不悄悄丢弃。

全部业务表和迁移记录均导出，快照目录和运行日志不递归打包。内容指纹排除纯技术 migrationHistory，用于判断 V1 转换后重复恢复是否真正改变业务数据；文件校验和整库写后复核仍包含迁移记录。

## 一致性与回滚

业务写入、每日励志语和备份恢复共用串行门。预检保存当前内容指纹，真正恢复前再次确认，防止预检后新增数据被误覆盖。

先保存并验证恢复前快照，再持久保存 prepared 日志，然后在单一 IndexedDB 事务中清除/写入全部表；文件操作和摘要计算放在事务之外。提交后整库复核，再持久化 committed 日志。

事务中途失败会原子回滚。提交后检查失败时补偿还原原数据并复核；任何不能确认的结果都暂停写入，重新打开时先检查完整前态/后态，必要时还原快照。不会用清库或数据库降版本代替恢复。

## 文件保护

原生文件对话框选择用户文件；预加载只暴露具体操作，不暴露任意文件系统接口。快照 ID 限制为 UUID，拒绝路径穿越和符号链接，导出禁止写入 Chromium profile。

先写同目录临时文件、同步并回读，再重命名。日常快照保留14份，重要/手动快照不自动删除；新快照未验证不轮换，损坏文件保留并提示。

## 验证范围

- 格式/版本/摘要、重复主键、清单数量、外键和同周期关系、合法日期和类型。
- 预计与实际独立，来源互斥，已确认计时检查重叠，仅时长补录注明无法核验。
- 重复恢复不追加，前置快照失败不写，事务中途失败整库保留，中断后重新打开检查。
- V1→V2 逐行保留旧数据；未保护升级阻止；迁移异常回到V1事务前态。
- 两万条跨2027—2029的任务、学习记录和计时片段，验证完整恢复和CSV准确性。

正式目录升级结果和人工验收记录单独记录，不把隔离测试等同于所有电脑均已验证。
